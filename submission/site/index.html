TOF Project Assistant

An accountable AI project manager for a small software consultancy. It turns a messy client brief into a validated plan, a quotation, and a UI screen inventory — and stops for human approval before anything is written to a shared file or sent to a client.

Source code on GitHub Accountability sheet End-to-end case study

The input

A brief forwarded from WhatsApp, not a specification

This is the actual starting point. No headings, no feature list, no deadline — and two requirements that cannot both be satisfied.

BS

“Oh iya satu lagi, di Sidoarjo kalau hujan deras internet suka mati. Jadi sistemnya harus tetap bisa dipakai walaupun internet mati. Tapi datanya saya pengin aman dan bisa dibuka dari mana-mana, jadi tolong simpan di Google Sheets online itu ya mas.”

“…mulai tanggal 1. Budget saya siapkan Rp 12 juta, kalau lebih saya mikir-mikir dulu.”

1contradiction the agent must surface, not silently resolve
5missing facts it must ask about instead of inventing
Rp 12 jtbudget the first honest estimate exceeds

A general-purpose assistant will produce a confident plan anyway — inventing the user count, guessing the deadline, and pricing work nobody agreed to. The gap between what the client says and what a developer needs is where projects fail, so that gap is where this agent is designed to stop.

How it works

Five steps, three of them end in a question

Every step leaves a file on disk, so any claim the agent makes can be checked against what it actually wrote.

1

Read the brief, then list what is missing

Finds the contradiction, the five gaps, and the budget conflict. It does not plan yet.

stops and asks brief.jsonclarifications.json
2

Build the plan, then validate it with code

WBS, effort, cost and risks. Every line is tagged [BRIEF], [CLARIFIED], [ASSUMPTION] or [AI RECOMMENDATION]. Six deterministic checks run before a human sees it.

stops for approval plan.jsonvalidation.json
3

Wait for a human decision

Nothing is written or sent until an approval card is resolved. A rejection returns a reason, the plan is revised rather than restarted, and a new card is issued — the old approval ID cannot be reused.

blocks execution approval-history/
4

On approval: write the tracker, generate the quotation

The Excel tracker is generated from the plan, then verified against it — phase drift and stale rows are detected instead of silently shipped. Quotation and email are two separate approvals.

tof-project-tracker.xlsxquotation-data.json
5

Derive UI screens from the plan — never from imagination

Each screen carries a derivedFrom pointer to the scope line that justifies it. If a screen has no source line, it is not drawn.

ui-spec.jsonscreens/*.png
The gate

The state machine that makes “approval” mean something

Enforced in gate.py, not in a prompt. Execution is refused unless the action is in APPROVED.

DRAFT→ PENDING_APPROVAL→ APPROVED→ EXECUTED
REJECTED→ DRAFT (revised)→ PENDING (new) remediation loop
FAILED needs a new approval to retry
Accountability

Five rules, each with a file that enforces it

A rule that lives only in a prompt is a suggestion. These are checks that can fail.

RuleWhat it means hereEnforced by
Shows sources Every plan line is tagged with where it came from. Assumptions are labelled as assumptions, never presented as facts. validator.py · INFORMATION_TRANSPARENCY
Stays within permissions A bounded authority table: it may analyse, propose and explain. It may not execute, send, or fabricate data. gate.py · check_risk_level
Asks before acting No external write without a resolved approval. Quotation and email are separate approvals, so consent to draft is not consent to send. gate.py · state machine
Admits limits One test fails on purpose and is documented. The tool reports what it could not do rather than skipping quietly. tests/test_cases.py · TC-002
Keeps a record Append-only JSONL. Every action has an ID, timestamp, actor and approval reference. audit_logger.py · 33 event types
Output

14 screens, every one traceable to a scope line

Derived from the approved plan for SG Garage — a workshop management system. Each card shows the scope line that justifies the screen, in the agent's own words.

Why this matters: an AI that invents screens also invents work — and work costs money. Visibility is scoped too: Service Advisor 8/14 · Kasir 4/14 · Kepala Bengkel 14/14.

The single failure is TC-002: keyword-based gap detection cannot match an LLM's semantic reading of a brief. It is reported rather than removed, because a suite that always shows 100% is a suite that is not measuring anything.

Limits

What this is not

Stated plainly, because the value of the approval gate depends on knowing where it ends.

Not a replacement for a project managerIt drafts and validates. Judgement, negotiation and client trust stay human.
Not a semantic gap detectorGap detection is keyword-based; that is the documented failing test.
Not an autonomous senderEmail and shared-file writes require a separate approval each time, by design.
Not a full design systemUI output is a screen inventory plus static mockups — no interactive prototype.
